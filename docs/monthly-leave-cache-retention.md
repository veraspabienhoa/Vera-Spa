# Monthly leave reads, coherent cache and technical retention

Production integration of the earlier performance examples:

- `GET /v2/leave/month-records?month=YYYY-MM&start=YYYY-MM-DD&end=YYYY-MM-DD` checks authentication and the current `leave`/penalty grants on every request. Optional dates must stay within the selected month. The legacy records endpoint remains available to existing reporting clients.
- The registration page uses this endpoint. Its list, daily statistics and export ranges are clipped to the selected date's month. Selecting another month changes the active month; cross-boundary week filters cannot fetch neighboring months. Employee filtering still sees the complete selected range, so counts and penalties are not partial-page totals.
- The cache stores only that month's projected record fields, never personnel payloads, identities, payment decisions or historical leave balances. It is bounded to 128 entries/8 MiB per API process, with a 15-second TTL and coalesced concurrent misses. HTTP responses use `private, no-store`.
- Transactional PostgreSQL statement triggers increment revisions once per changed month. Inserts, updates, deletes, bulk imports, month moves and truncation invalidate all processes after commit. Rollbacks do not change the revision. The loader reads the version and rows in a repeatable-read snapshot. No DB connection is held while waiting for another cache loader.
- Migration is explicit (`python vera_leave_month_schema.py --apply`), with short lock/statement timeouts and a concurrent partial index. API reads never run DDL. Before migration, the new endpoint works with uncached month-bounded reads. Existing date/employee indexes serve the leave window.
- `python vera_technical_retention.py` previews counts; `--apply` deletes at most 20 batches of 500 completed `live_tour_projection` jobs older than 72 hours. It skips row locks and active leases. Invoices, reports, request receipts, recovery/edit audits, leave records, pending/retry/failed jobs and other queues are preserved.
- `.github/workflows/technical-history-retention.yml` schedules cleanup hourly at minute 17 UTC using existing production SSH access. GitHub schedules may start late. It uses the running release, verifies migration, serializes against production deployment, and has a process timeout. No second OS cron is installed.
- The deployment workflow runs PostgreSQL regressions, deploys the tested SHA, applies/verifies the migration, and previews/applies/verifies the first cleanup. Logs contain only counts and version state.

Rollback: revert the application commit to return to legacy reads, and disable the scheduled workflow. The revision table/triggers can remain safely until a separately reviewed migration removes them. Removing cache integration does not require deleting business records. Deleted completed technical jobs cannot be restored except from backup; they do not hold invoice or audit authority.

Verification: isolated PostgreSQL tests cover month boundaries, rollback, bulk writes, deletion, truncation, multiple cache instances, pre-migration fallback, permission revocation, penalty redaction and locked cleanup rows. React tests cover range clamping, canceled obsolete reads, inline edits and save-refresh failures. Real production verification logs counts only; it does not submit a synthetic financial or leave mutation.
